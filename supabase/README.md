# إعداد Supabase لـ BSCH Clinics

هذا المجلد يحتوي على مخطط PostgreSQL مبدئي، ولم يتم تطبيقه تلقائياً على أي مشروع. راجع أولاً [تقرير الفجوات](../docs/SUPABASE-GAP-REPORT.md).

## المتطلبات

يلزم مشروع Supabase يحدده صاحب المشروع، ونسخة احتياطية قبل التطبيق. لا تضع `service_role` أو كلمة مرور قاعدة البيانات أو أي Secret داخل GitHub أو APK.

القيم العامة المسموح أن تصل إلى الواجهة لاحقاً هي:

```env
SUPABASE_URL=https://<project-ref>.supabase.co
SUPABASE_ANON_KEY=<public-anon-key>
```

أما مفاتيح الإدارة أو اتصال PostgreSQL فتستخدم فقط في بيئة خادم آمنة أو أداة ترحيل محلية مؤقتة، ولا ترفع إلى المستودع.

## التطبيق

من لوحة Supabase SQL Editor أو Supabase CLI، راجع ثم طبّق:

```text
supabase/migrations/0001_initial_schema.sql
```

المخطط ينشئ الجداول الرئيسية، العلاقات، الفهارس، أنواع الأدوار والحالات، RLS، ودالتين آمنتين للحجز والاستعلام العام. الحجز العام لا يستخدم INSERT مباشراً من المتصفح، ويعيد رمز وصول عشوائياً يجب حفظه لدى العميل. الاستعلام يتطلب رقم الحجز والرمز، وليس رقم الهاتف وحده.

## Auth والأدوار

أنشئ حسابات الموظفين من Supabase Auth بعد مراجعة سياسة الحسابات. بعد إنشاء المستخدم، يجب إنشاء صف مطابق في `public.profiles` بمعرف `auth.users.id` ودور من `founder` أو `booking` أو `doctor` أو `nurse`. لا تعتمد على الحسابات الافتراضية الموجودة في SQLite.

## ما لم يُنقل بعد

هذا الملف لا يجعل Flask Serverless تلقائياً. المسارات المعقدة، تأكيد الحجز، تغيير الحالة، إدارة الطابور، التقارير والتصدير، التدقيق، parsing الرسائل، وأي تكاملات خارجية تحتاج Edge Functions أو Backend موثوق قبل حذف Flask. لا تحذف Backend الحالي بناءً على وجود هذا المخطط فقط.

## الترحيل

لا تشغّل ترحيل بيانات مرضى حقيقية على مشروع تجريبي. استخدم نسخة Demo أو نسخة يصرح بها صاحب المشروع، ثم تحقق من عدد الصفوف والعلاقات. قاعدة SQLite الحالية لا تُحذف من خلال هذه المرحلة.
